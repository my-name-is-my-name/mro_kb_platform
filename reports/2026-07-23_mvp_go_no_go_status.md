# Срез работ: MVP Go / No-Go

Дата: 2026-07-23

## Цель MVP

Быстро первично классифицировать новую заявку заказчика: можно ли рассматривать её в работе, нужно ли сразу отказать, запросить исходные данные или передать на экспертную проверку.

## Выполнено

- Реализован сервис первичного разбора заявки `mro-go-no-go`.
- Подключен формальный источник полномочий — сертификат с перечнем ATA-разделов.
- Реализовано извлечение прямых ATA из текста и эвристическое определение связанных ATA по объекту и характеру работ.
- Добавлена проверка применимости области сертификата.
- Добавлена проверка полноты исходных данных: тип ВС, объект работ, размеры и координаты повреждения, фотографии, применимая документация.
- Реализованы статусы: `go_to_assessment`, `no_go`, `need_more_info`, `hold_expert_review`.
- Реализован поиск внутренних материалов и похожих заявок в `data/output`; найденные документы выдаются как доказательная база, а не как автоматическое разрешение.
- Сервис `mro-similar-cases` существует отдельно; его специализированное ранжирование пока не включено непосредственно в маршрут Go/No-Go.
- Добавлен OpenAI-совместимый API и отдельный endpoint `/api/triage`.
- API запущен на `10.100.112.51:8122`; проверен ответ через `/v1/chat/completions`.
- Исправлен формат ответа для OpenWebUI: результат теперь передаётся и в текстовом поле `choices.message.content`.
- Добавлены базовые автотесты сценариев сертификата, неполных данных, связанных ATA и поиска локальных материалов.
- Подготовлено ТЗ на развёртывание T-Search как отдельного слоя поиска технических документов.

## Текущая логика решения

1. Система извлекает факты из текста заявки и определяет прямые и потенциально связанные ATA.
2. Сверяет предмет работ с областью сертификата.
3. Проверяет обязательные исходные данные.
4. Ищет внутренние прецеденты и технические материалы.
5. Формирует решение и досье для эксперта: основания, риски, недостающие данные, требуемые документы и ссылки на найденные материалы.

Автоматическое положительное решение намеренно консервативно. Эксперт остаётся обязательным подтверждающим звеном.

## Ограничения текущего MVP

- Сертификат содержит преимущественно ATA-область, но не все ограничения по типам ВС, видам работ и условиям одобрения.
- Поиск по локальным материалам пока лексический; его точность будет расти при добавлении метаданных и T-Search.
- AMM, SRM, CMM, ALS, AD/SB и эксплуатационная документация ещё не загружены как полноценный структурированный корпус.
- Оценка трудоёмкости и цены не входит в текущий этап.
- Ответ OpenWebUI зависит от корректной настройки его OpenAI-подключения к API `http://10.100.112.51:8122/v1`.

## Варианты дальнейшего развития

### 1. Усилить rule-based MVP

Расширить матрицу полномочий: тип ВС, модификации, виды работ, ограничения и необходимые подтверждающие документы. Добавить каталог обязательных данных для типовых классов заявок.

Преимущество: максимальная объяснимость и предсказуемость решений.

### 2. Добавить слой интеллектуального поиска

Развернуть T-Search для поиска по загружаемым AMM/SRM/CMM/ALS, директивам, бюллетеням и внутренней документации. Поиск должен возвращать цитируемые фрагменты, метаданные применимости и уровень доверия.

Преимущество: быстрее находить релевантные основания и скрытые связи между ATA.

### 3. Создать контролируемого собственного агента

Агент не принимает инженерное решение самостоятельно. Он исполняет фиксированный workflow: собирает доказательства, ищет документы, выявляет пробелы, формирует вопросы и передаёт досье эксперту. Доступ — только к белому списку read-only инструментов.

Преимущество: автоматизация многошагового поиска при сохранении контроля и аудита.

### 4. Добавить расчёт трудоёмкости и цены

После стабилизации Go/No-Go использовать подтверждённые исторические заявки и декомпозицию работ для оценки трудозатрат, сроков и цены. Результат должен показывать аналоги, коэффициенты и допущения.

## Ближайший план

1. Проверить и закрепить настройку OpenWebUI для модели `mro-go-no-go`.
2. Собрать экспертную матрицу: тип ВС × ATA × вид работ × разрешения × обязательные документы.
3. Описать шаблоны заявок и минимальные наборы входных данных для ремонта, изменения, анализа и выпуска документации.
4. Подготовить и загрузить первый приоритетный корпус AMM/SRM/CMM/ALS с метаданными ВС, ATA, ревизии и применимости.
5. Интегрировать `mro-similar-cases` в Go/No-Go как отдельный источник исторических аналогов. В выдаче должны быть: ссылка на заявку-аналог, совпавшие признаки, релевантные ATA, исход и трудозатраты при наличии. Аналоги используются только как доказательство и ориентир: они не отменяют ограничения сертификата и обязательность исходных данных.
6. Развернуть T-Search по подготовленному ТЗ и сравнить его качество с текущим поиском на исторических заявках.
7. Провести экспертную валидацию на выборке закрытых заявок: измерить корректность статуса, полноту выявленных ATA и качество списка запрашиваемых данных.
8. После валидации начать проектирование модуля оценки трудоёмкости и цены.
