# План разработки специализированного веб-сервиса Go / No-Go

Дата: 2026-07-23

## Назначение

Заменить OpenWebUI в основном рабочем процессе специализированным сервисом для регистрации MRO-заявок, первичной проверки Go / No-Go, сбора доказательств и обязательного экспертного решения.

OpenWebUI остаётся необязательным вспомогательным интерфейсом для диалогового поиска по базе знаний. Он не является системой учёта заявок и согласований.

## Целевой процесс

```text
Черновик → Проверка комплектности → Автоматическая оценка
  ├─ Запросить информацию → Проверка комплектности
  ├─ Экспертная проверка → Go: принять к оценке
  └─ No-Go: отказать
```

`Go` означает только допуск к оценке трудоёмкости и цены. Окончательные `Go` и `No-Go` подтверждает эксперт; автоматическая рекомендация не заменяет инженерное решение.

## Целевая архитектура

```text
Web UI
  ↓
Application API / workflow заявок
  ├─ Rule engine Go/No-Go
  ├─ Similar-cases adapter
  ├─ Evidence search adapter: SQLite → T-Search
  ├─ Attachments и document registry
  └─ Роли, уведомления и аудит
  ↓
Operational DB                  Knowledge DB / поисковые индексы
заявки, решения, аудит          документы, аналоги, embeddings
```

Текущие сервисы сохраняют границы ответственности:

- `GoNoGoService` — детерминированная рекомендация, не запись рабочего процесса;
- `CommercialOffersService` — read-only поиск исторических аналогов;
- T-Search — read-only поиск доказательств по AMM/SRM/CMM/ALS/AD/SB;
- внешний интернет-поиск — только кандидат на источник до фиксации версии и проверки экспертом.

## Ограниченный агентский режим поиска ATA и доказательств

Для определения ATA используется не набор предметных условий в коде, а последовательный управляемый workflow:

```text
Заявка и поля
  → итерация 1: каталог сертификата ATA + экспертные синонимы
  → кандидаты ATA с объяснением совпадения
  → поиск AMM/SRM/CMM/ALS и внутренних материалов по каждому кандидату
  → итерация 2: извлечение ATA из найденных источников и правила связей
  → досье: подтверждённые ATA, гипотезы, источники и вопросы эксперту
```

Правила режима:

- список ATA сертификата является первым каталогом-кандидатом, а не только финальной проверкой полномочий;
- синонимы компонентов, связи ATA и условия их применения хранятся в версионируемом экспертном каталоге, а не в Python-коде;
- второй проход может только предложить связанные ATA; он не подтверждает применимость без документа или эксперта;
- AMM/SRM/CMM/ALS, AD/SB и внутренние заключения возвращаются с ревизией, применимостью и ссылкой на фрагмент;
- LLM/T-Search разрешено использовать для поиска и извлечения кандидатов, но не для окончательного инженерного решения;
- каждый шаг записывает запрос, найденные источники, версию каталога и причину включения ATA в аудит оценки.

## Сущности MVP

- `Request`: заявка, заказчик, тип ВС/MSN/регистрация, описание, тип работ, текущий статус.
- `RequestFact` и `AffectedATA`: извлечённые факты, прямые/предполагаемые ATA, уверенность и причина связи.
- `Attachment`: исходный файл, хэш, тип, OCR-статус, источник и автор загрузки.
- `Assessment`: версия автоматической оценки, правило/версия сертификата, рекомендации и доказательства.
- `EvidenceDocument` и `EvidenceFragment`: документ, ревизия, применимость, ATA, тип ВС, фрагмент, ссылка и статус доверия.
- `HistoricalCase`: исторический аналог, совпадения/различия, исход, трудоёмкость и цена при наличии.
- `ExpertDecision`: подтверждение или изменение рекомендации с обязательным комментарием.
- `AuditEvent`: неизменяемая история действий, изменений данных и решений.

## Этапы разработки

### Этап 0. Проектирование и подготовка

Результат: утверждённые статусы, роли, минимальные поля заявок, модель данных, матрица прав и прототип экранов.

Нужно согласовать с экспертами:

- матрицу «тип работ × обязательные исходные данные»;
- правила маршрутизации к экспертам;
- содержание официального отказа и запроса информации;
- минимальный состав карточки ремонта и карточки изменения.

### Этап 1. Каркас рабочего процесса

Результат: пользователь может создать заявку, приложить документы, увидеть реестр и пройти статусы до экспертной проверки.

- отдельная operational DB, не смешанная с текущей базой знаний;
- авторизация и роли: заказчик, менеджер, эксперт, администратор;
- реестр и карточка заявки;
- загрузка вложений, контроль типов и хэшей;
- аудит изменений и назначение ответственного.

### Этап 2. Интеграция Go/No-Go

Результат: из карточки запускается текущий rule engine, а результат сохраняется как версия оценки.

- endpoint `POST /api/requests/{id}/triage`;
- отображение ATA, применимости сертификата, пробелов, рисков и вопросов;
- структурированный запрос дополнительных данных заказчику;
- запрет финальных статусов без экспертного подтверждения.
- внедрение ограниченного агентского режима поиска ATA: каталог → документы → связанные ATA → экспертное досье.

### Этап 3. Досье эксперта и исторические аналоги

Результат: эксперт видит единый пакет оснований и подтверждает/корректирует решение.

- endpoint `POST /api/requests/{id}/similar-cases`;
- отдельная вкладка «Исторические аналоги»;
- поиск и отображение внутренних документов;
- обязательный комментарий, если эксперт изменяет рекомендацию;
- экспорт досье в Markdown/PDF.

Исторический аналог не может отменить ограничения сертификата, требования AD/SB или отсутствие исходных данных.

### Этап 4. Управление техническими документами и T-Search

Результат: AMM/SRM/CMM/ALS/AD/SB загружаются, получают метаданные и безопасно ищутся по применимости.

- реестр документов: тип ВС, ATA, ревизия, дата действия, издатель, хэш, статус доверия;
- контролируемая индексация и фильтрация по применимости;
- подключение T-Search через read-only адаптер;
- shadow-тест на 30–50 закрытых экспертных заявках;
- источник без ревизии, оригинала или подтверждённой связи отображается как предупреждение, а не как основание решения.

### Этап 5. Валидация и подготовка расчёта цены

Результат: подтверждена корректность Go/No-Go на истории и подготовлены данные для трудоёмкости/цены.

- проверка на выборке закрытых заявок;
- метрики: точность статуса, полнота ATA, доля корректно выявленных недостающих данных, время до экспертного решения;
- фиксация версии правил и сертификата для каждого решения;
- после накопления подтверждённых данных — отдельный модуль оценки трудоёмкости и цены.

## Рабочие потоки и распределение исполнения

| Поток | Зона ответственности | Результат |
|---|---|---|
| Backend/workflow | Operational DB, API заявок, статусы, аудит, роли | надёжный процесс без зависимости от UI |
| Frontend/UX | реестр, карточка, досье эксперта, запрос данных | удобный рабочий интерфейс вместо чата |
| Domain rules | сертификат, ATA, обязательные входные данные, тест-кейсы | версионируемые и проверяемые правила |
| Evidence/search | документы, `mro-similar-cases`, T-Search, метаданные | доказательная база с указанием применимости |
| QA и эксперты | историческая выборка, критерии, приёмка | подтверждённое качество и обратная связь |

Потоки Backend/workflow, Frontend/UX и Evidence/search можно вести параллельно после утверждения модели данных и API-контракта. Domain rules требует постоянного участия назначенного инженерного владельца.

## Минимальный API

- `POST /api/requests`, `GET /api/requests`, `GET/PATCH /api/requests/{id}`
- `POST /api/requests/{id}/attachments`
- `POST /api/requests/{id}/triage`
- `GET /api/requests/{id}/assessments`
- `POST /api/requests/{id}/expert-decision`
- `POST /api/requests/{id}/similar-cases`
- `POST /api/requests/{id}/evidence-search`
- `GET /api/requests/{id}/dossier`

## Критерии приёмки MVP

- Заявка создаётся с обязательными полями и вложениями.
- Система явно показывает, каких данных не хватает для конкретного вида работ.
- В досье есть рекомендация, ATA, сертификатная применимость, доказательства и исторические аналоги.
- Эксперт может подтвердить или изменить решение; изменение невозможно без комментария.
- Финальный `Go`/`No-Go` невозможен без экспертного подтверждения.
- Все действия и версии оценок записаны в аудит.
- Аналоги, LLM и T-Search не обходят блокирующие правила и не являются окончательным инженерным основанием.
